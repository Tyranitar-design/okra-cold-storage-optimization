# 管理信息系统与数据库设计 v1

更新日期：2026-05-27

## 1. 系统目标

Web 平台最终应是一个完整的冷库布局优化管理信息系统，而不是只展示结果的页面。它需要支持数据管理、地图可视化、优化实验、算法分析、结果解释、论文证据追踪和物流项目联动。

## 1.1 连接状态定义

系统状态建议分三层：

1. 配置完成：`OKRA_DATABASE_URL` 已设置。
2. 可探测：`/api/v1/db/probe` 返回 `probe_attempted=true`。
3. 真连通：`probe_ok=true`，且 `probe_current_database` / `probe_current_user` 非空。

只有第三层才能把关键接口对外表述为 `source_backend=database`。

## 1.2 入库预览

系统建议提供一个只读的 seed 预览视图，至少展示：

- 计划写入的总行数
- 非空表数量
- Top N 表名与行数

这有助于在真正 `--apply` 之前确认数据规模和表结构是否符合预期。

接口示例：

```powershell
/api/v1/db/seed-preview
```

## 2. 技术建议

| 层级 | 技术 |
| --- | --- |
| 数据库 | PostgreSQL + PostGIS |
| 后端 | FastAPI + SQLAlchemy / SQLModel + Alembic |
| 异步任务 | Celery/RQ 或 FastAPI BackgroundTasks 起步 |
| 前端 | Vue/React + TypeScript |
| 地图 | Leaflet / Mapbox / 腾讯地图 / 高德地图，按可用 API 决定 |
| 图表 | ECharts / Plotly |
| 优化服务 | Python + Gurobi |
| 物流联动 | REST adapter，对接现有物流路径规划项目 |

## 4. PostgreSQL / PostGIS 表设计草案

### 4.1 数据源与证据

| 表 | 用途 |
| --- | --- |
| `data_sources` | 记录所有数据来源、级别、许可、访问日期 |
| `literature_sources` | 记录文献、DOI、参数、结论、引用格式 |
| `parameter_evidence` | 参数值与文献或数据源的映射 |
| `artifact_registry` | 图表、结果文件、论文结论和数据源的映射 |

### 4.2 空间与业务数据

| 表 | 关键字段 |
| --- | --- |
| `nodes` | node_id, name, level, production_ton, geom, population, road_access |
| `candidate_sites` | site_id, node_id, site_type, is_active, geom |
| `cold_storage_types` | type_code, temp_min, temp_max, energy_kwh_per_ton, carbon_factor |
| `capacity_options` | type_code, capacity_ton, fixed_cost, operating_cost |
| `distance_matrix` | origin_id, destination_id, distance_km, source_id |
| `transport_time_matrix` | origin_id, destination_id, time_h, source_id |

### 4.3 实验与优化结果

| 表 | 关键字段 |
| --- | --- |
| `optimization_experiments` | experiment_id, name, model_type, data_version, status, config_json |
| `optimization_runs` | run_id, experiment_id, started_at, ended_at, solver, mip_gap, runtime_sec |
| `solution_facilities` | run_id, site_id, type_code, capacity_ton, assigned_ton, utilization |
| `solution_assignments` | run_id, demand_node_id, facility_site_id, assigned_ton, transport_time_h |
| `solution_metrics` | run_id, total_cost, fixed_cost, operate_cost, transport_cost, loss_cost, carbon_cost, violations |
| `sensitivity_results` | run_id, sweep_variable, sweep_value, metrics_json |
| `pareto_solutions` | run_id, cost, loss_ton, carbon_ton, is_nondominated |
| `benders_iterations` | run_id, iter_no, lower_bound, upper_bound, gap_pct, cuts_added |
| `ai_benders_cut_scores` | run_id, iter_no, cut_id, features_json, score, selected |

### 4.4 企业数据预留

| 表 | 关键字段 |
| --- | --- |
| `enterprise_batches` | batch_id, origin_node, harvest_time, weight_ton, grade, anonymized_org |
| `enterprise_storage_logs` | batch_id, storage_id, temp, humidity, in_time, out_time |
| `enterprise_transport_logs` | batch_id, vehicle_id, origin, destination, depart_time, arrive_time |
| `enterprise_quality_records` | batch_id, loss_weight, spoilage_rate, quality_score |

## 6. 与物流系统的接口契约

建议先定义适配器，而不是直接强耦合。

### 6.1 输出给物流系统

```json
{
  "scenario_id": "baseline_v2_1",
  "facilities": [
    {
      "facility_id": "C1",
      "type": "frozen",
      "capacity_ton": 200,
      "lat": 29.337,
      "lon": 111.725
    }
  ],
  "demands": [
    {
      "node_id": "V1",
      "demand_ton": 12.3,
      "assigned_facility": "C1",
      "lat": 29.1,
      "lon": 111.5
    }
  ],
  "constraints": {
    "temperature_chain": true,
    "max_precool_time_h": 2.0
  }
}
```

### 6.2 接收物流系统结果

```json
{
  "route_plan_id": "vrp_001",
  "scenario_id": "baseline_v2_1",
  "total_distance_km": 123.4,
  "total_time_h": 5.6,
  "vehicle_count": 4,
  "routes": []
}
```

## 7. 开发顺序

1. 建立 PostgreSQL schema 和本地配置。
2. 将当前 csv/pkl 结果导入数据库。
3. 后端 API 从读文件迁移为读数据库。
4. 前端建立总览、地图、数据管理、实验中心四个基础页面。
5. 增加异步优化任务。
6. 增加物流系统 adapter。
7. 增加文献证据库和论文图表追踪。

## 8. 质量要求

1. 每个 API 有 Pydantic schema。
2. 每个核心表有唯一键和数据来源字段。
3. 所有实验结果可从数据库追溯到原始数据源。
4. Web 页面不能只展示硬编码数据。
5. 地图图层必须标注坐标来源和距离/时间估算方式。
6. 与物流系统的接口先 mock 测试，再接真实服务。
